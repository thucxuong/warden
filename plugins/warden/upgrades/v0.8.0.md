Task worktrees move into the project: `<main>/.worktrees/<task>` instead of `<parent>/<repo>.worktrees/<task>`. Runs started before this upgrade keep their old worktrees; do not move them.
1. If `.gitignore` has no line `.worktrees/` (or `.worktrees`, `/.worktrees`, `/.worktrees/`), add the line `.worktrees/` at the end. It is committed with this upgrade. Then run `git check-ignore -q .worktrees/` in the main checkout; it must exit 0. `warden start --worktree` refuses while git does not ignore the folder.
2. Leave the entry `<parent>/<repo>.worktrees` in `permissions.additionalDirectories` of `.claude/settings.local.json` as it is: runs started before the upgrade still edit there. Tell the user they can remove it, and the empty folder, once `git worktree list` shows no worktree under `<parent>/<repo>.worktrees/` (`warden clean` removes the shipped ones).
3. Tools run in the main checkout now find `.worktrees/` inside it, with a full copy of the code per task. For each tool config in the project, if the tool would scan `.worktrees/`, add it to its ignore list. Leave a config alone when it already skips the folder (it reads `.gitignore`, or it only includes your own folders such as `src/**`). The common ones:
   - Vitest: in `vitest.config.*`, `test.exclude: [...configDefaults.exclude, ".worktrees/**"]` (import `configDefaults` from `vitest/config`; keep any existing entries).
   - Jest: add `"<rootDir>/.worktrees/"` to `testPathIgnorePatterns` and to `modulePathIgnorePatterns`.
   - ESLint: in a flat config, add `".worktrees/**"` to the global `ignores` entry (create `{ ignores: [".worktrees/**"] }` if there is none); with `.eslintignore`, add the line `.worktrees`.
   - Prettier: version 3 reads `.gitignore`, so nothing to do. With an older version and a `.prettierignore`, add the line `.worktrees`.
   - Playwright: when `testDir` is the repo root or not set, add `"**/.worktrees/**"` to `testIgnore`.
   - Any other tool that walks the tree from the main checkout (stylelint, knip, a coverage tool, the project's own tools in `.warden/tools/` such as a code graph): add `.worktrees` to its ignore list or skip that folder in its code.
   TypeScript needs nothing: `tsc` skips dot folders. Do not add an `exclude` to `tsconfig.json`; it drops the default that leaves out `outDir`.
   Show the user each change. Then tell the user, without changing anything: each worktree also sees the main checkout's `node_modules`, so a dependency the branch removed can still resolve. A dependency check as a gate (for example ESLint `import/no-extraneous-dependencies`, or `knip`) catches it.
4. Optional, with the user's OK: run `warden clean --dry-run`, show the user its lines, then run `warden clean`.
5. Optional, only with the user's OK: ticket tools may now have `create` and `link` (the contract is in the warden:tools skill, section Roles). If `.warden/tools/roles.json` has a `tickets` role, ask the user once whether to add them to that tool. If they say no, or there is no such role, skip this step. If yes:
   - Add `create --title <t> --type <type> --body-file <path> [--epic <id>] [--blocked-by <id,id>]`. It makes the ticket, picks the id itself (for a file tool: one more than the highest number used by a ticket or by a folder in `.warden/state/` or `.warden/history/`, same prefix and width; for a tracker: the id the tracker gives), and prints `{ ticket, changed }`: `ticket` is the new ticket with `body` set to the text of the body file, `changed` the repo paths it wrote (`[]` for a tracker outside the repo). A non-epic id must match `taskIdPattern`. A new ticket is `todo`. Bad input is exit 1, never exit 2.
   - Only for a tracker outside the repo, add `link <id> <url>`. It records the url on the ticket and prints `{ id }`. A second call with the same url changes nothing. It must not change repo files. A tool that keeps tickets as repo files skips it: the pull request already carries the ticket change.
   - Add these two lines after `SetStatusResult` in `.warden/tools/tool.ts`, if they are not there: `export interface CreateResult { ticket: TicketDetail; changed: string[] }` and `export interface LinkResult { id: string }`.
   - Try them: write a scratch file with one line of text, run `warden orchestrate create --title "Upgrade test" --type chore --body-file <file>`, then remove that ticket again (delete its file, or close it in the tracker). With `link`, run `warden tools tickets link <an existing id> https://example.com/pr/1` twice, then undo the change.
   - Run `warden tools --check`; it must exit 0. Commit the tool changes with this upgrade.
