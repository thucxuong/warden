Every warden run starts from a ticket now: `warden start <id>` reads the task from the ticket tool (the `tickets` role), and `--text`, `--text-file` and `--ticket` are gone. The ticket tool must have `create`. Runs started before this upgrade keep working: the engine finishes them as before.

1. If `.warden/tools/roles.json` has no `tickets` role, write a ticket tool. First run `warden status`: `roles.json` cannot change while a run is live. If it lists live runs, leave `roles.json` as it is in the bullet below, run `warden tools backlog create` (with no flags it must exit 1, not 2) instead of `warden tools --check`, and tell the user to set the role once those runs are done. Ask the user where the tickets live: as Markdown files in this repo (recommended when there is no tracker), or in a tracker such as Jira, Linear, GitHub or Azure DevOps.
   - Files: write `.warden/tools/backlog.ts` by copying the complete example in the warden:tools skill's `ticket-tool-example.md` (`../tools/ticket-tool-example.md` from this skill's base directory); the `tickets` contract is in that skill. Each ticket is `backlog/<ID>.md`: a header between two `---` lines with `title`, `status`, `type`, and optional `epic` and `blocked_by` (ids, comma-separated), then the body. Paths are relative to the checkout the tool runs in. `create` picks one more than the highest number used by a ticket or by a folder in `.warden/state/` or `.warden/history/`, with the same prefix and width; the first id is in the form of `taskIdPattern` in `.warden/warden.json` (for `^PG-\d{3}$`: `PG-001`). Add it to the array in `.warden/tools/index.ts`, and set `"tickets": "backlog"` in `.warden/tools/roles.json`. Then run `warden tools --check`: it must exit 0. Show the user the output.
   - A tracker: tell the user to run `/warden:tools` after this upgrade to write the tool for it. Until then `warden start` refuses. Skip step 2.
2. If `warden tools --check` shows `role tickets create` as `FAIL`, the tickets tool has no `create`: add it as the `create` branch of the example in the warden:tools skill's `ticket-tool-example.md` does. It makes the ticket, picks the id itself (for a file tool: one more than the highest number used by a ticket or by a folder in `.warden/state/` or `.warden/history/`, same prefix and width; for a tracker: the id the tracker gives), and prints `{ ticket, changed }`. Missing flags or other bad input is exit 1, never exit 2. Run `warden tools --check` again: it must exit 0.
3. Run `warden status`. For each live run, read `.warden/state/<id>/run.json`. If it has no `"ticket": true`, the run may have started from text. Run `warden tools tickets show <id>` (`warden tools backlog show <id>` while the role is not set yet): if it exits 0, the ticket exists, so leave it as it is. Only if it exits 3 (unknown ticket), add one by hand in the ticket tool with the same id. Title: the first line of `.warden/state/<id>/task.md`; body: the rest of that file; status `doing`; type `feature` when `flowName` is `feature`, `bug` when it is `bugfix`, else `chore`. For a file tool, write `backlog/<id>.md` in the format of the tool's other tickets; it is committed on the main branch with this upgrade. If the tool cannot take an id you choose (a tracker picks its own), tell the user which runs have no ticket and skip them. Either way those runs keep working. Warden does not set their tickets to done at ship: tell the user to run `warden orchestrate set-status <id> done` after each one is merged, then commit the paths it prints in `changed` on the main branch.
4. Commit the new and changed tool files and tickets with this upgrade.
