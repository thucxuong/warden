Warden

A simple, self-contained Claude Code harness that consumer projects install, follow, report to, and upgrade from.

WA — Warden Agent. Runs in this repo. Acts as an open-source maintainer.
CP — Consumer Project. Any repo that installs warden.
CPA — Consumer Project Agent. Claude working inside a CP.

1. Goal & principles

  • As simple as possible. No server, no build step. The opposite of the current harness repo (~53k files).
  • Claude Code only for now.
  • Tailored to software delivery: immediate action, feature flow, bugfix flow.
  • Traceable at high level, visible in the CP — not in warden.
  • Warden is hidden from the CPA: no repo link, no issue numbers, no warden code in the CP.
  • CP adopts warden's structure; the CPA builds its own project tools (snowflakes) to adapt.
  • Every doc has one purpose. No "this or that" — each kind of information has exactly one home.

2. Install & upgrade

Install (manual, once)

Warden is a Claude Code plugin. Install via the plugin marketplace, then run:

/warden:init

Creates .warden/, registers the CP on this machine.

Upgrade (automatic + guided)

  • Plugin auto-update replaces warden code.
  • /warden:upgrade applies structure changes. The warden script hands the steps to the CPA as text — never a repo link.
  • Warden code lives only in the plugin cache, never in the CP.

3. Workflows

/warden:doImmediate action — small task
/warden:featureFeature implementation
/warden:bugfixExtra prefix steps, then the feature flow

Each step writes one line to tasks/<ticket-id>.md. Steps marked amber are bugfix-only.

Rules for keeping it lean as it grows

  • Every folder has an INDEX.md — one line per file. The agent reads the index first, opens only what it needs.
  • Each file stays under ~200 lines; past that it is split by topic.
  • Shipped tasks move to tasks/done/.

6. Session start (silent)

A warden hook runs on every CPA session start and does three things:

  1. Gets the status of this CP's reports and compares it with reports.md.
  2. Checks whether the retro is due (2 days).
  3. Checks whether a newer warden version exists.

The CPA then gives the user a short heads-up:

R-0012 fixed in v0.4.0 — upgrade recommended
R-0015 marked project-specific — build it as a local tool
Retro due (last run 2 days ago)

7. Reporting — warden stays hidden

  • Only WA creates issues. The CPA writes the report; the warden script gives it an ID and hands it to WA on this machine right away (no waiting).
  • The link between report IDs and issue numbers stays on the warden side.
  • The CPA only ever sees report IDs and plain status — no URLs, issue numbers or repo names.
  • Hiding is "don't tell", not a lock. No extra blocking rule — decided: not needed.
