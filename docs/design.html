Warden

A simple, self-contained Claude Code harness that consumer projects install, follow, report to, and upgrade from.

WA — Warden Agent. Runs in this repo. Acts as an open-source maintainer.
CP — Consumer Project. Any repo that installs warden.
CPA — Consumer Project Agent. Claude working inside a CP.

1. Goal & principles

  • As simple as possible. Much smaller than the current harness repo.
  • Claude Code only for now. Not for community use — internal team tool.
  • Code runs the workflow, JSON holds progress. The CPA does creative work; the warden engine runs every gate.
  • Warden says what a step must achieve; the CP says how it runs internally (verify differs per CP).
  • Warden is hidden from the CPA: no repo link, no issue numbers, no warden code in the CP.
  • Every doc has one purpose. Each kind of information has exactly one home.
  • Stack: Bun + TypeScript 7. Built-ins only. Bun runs .ts directly (~5–10 ms startup), Bun.$ for gh/git. TypeScript 7 is a dev-only type checker in the warden repo. Strict mode, no runtime npm dependencies, one file per command. bun build --compile stays later; revisit Rust once stable.
  • Task IDs: each CP chooses its own format (in warden.json). Warden itself uses WD-xxxx.

2. Install, onboarding & upgrade

Install

Install Bun, then the warden Claude Code plugin from the private marketplace on the stable branch. Per person: 2 commands. Per team: write to .claude/settings.json; init writes the plugin on request.

Onboarding — one run

/warden:init scans the stack, drafts context/ and steps.json (check commands it finds), asks the user to confirm, done. No phases.

Upgrade

Plugin auto-update replaces warden code. Session start says when a newer version is in the marketplace clone (no network) and when the project layout needs /warden:upgrade.

3. The engine — the CPA never runs the gates

A small Bun program owns progress. The CPA does the creative work only (analyse, plan, implement, fix). Checks, triage and review are run by the engine, so they cannot be skipped.

1. warden next — current step + what it needs
2. CPA does the work
3. warden done — hands back output JSON
4. Engine validates the output and evidence, runs gates, moves forward or routes back

How the CP says "how" — .warden/steps.json

  • Check steps (verify, e2e…): just commands. The engine runs them; exit code is the evidence.
  • Agent steps (plan, implement…): the CP's instructions + the required output format.

4. Workflows — the CPA composes its own

Step catalog (from warden)

analyze plan implement check review approve ship

Indigo = agent step · green = engine-run gate · amber = human approval

Each type has a clear input, output and evidence. /warden:compose lets the CPA build a workflow JSON for the task — and use it right away.

Starting templates

do implement → check
feature plan → implement → check → review → ship
bugfix reproduce → diagnose → feature flow
chore implement → check → ship

warden flow check — the linter

Warden doesn't fix the workflow shape; it only lints it:

  • Gates come after the last code step: check, then review if any. One ship step last.
  • Limits (fixer rounds, review rounds) cannot be raised. Unknown keys rejected.
  • Approval steps are skipped only when the session that runs the task was started with PROJECT_AGENT=1 (recorded by a hook).

5. Planning — recursive task breakdown

From the harness recursive-task-breakdown skill. The agent works freely, but must drill down until every building block is visible.

  1. List what already exists (the "factor pool": repo, tools, deps).
  2. Break the task into leaves; each is reuse · configure · compose · adopt · build.
  3. Keep breaking down until every leaf's inputs exist or come from an earlier step.
  4. Independent steps become waves.

Kept from harness writing rules: no placeholders, self-review.

6. Self-healing (from the reference app, simplified)

  1. A check fails → engine runs triage: re-run the failed check on a clean copy of the main branch at the ticket's base commit.
  2. After a fix lands, the engine merges main into the ticket branch.
  3. A flaky failure stops for a person; no fixer handles it.
  4. Rules in triage-rules.json label a failure and point to its fix note; they never decide the verdict and must be narrow.
  5. The fixer never edits steps.json; setup lives in scripts/warden-setup.sh, which it may fix. A needed check-command change is GAVE_UP for a person.
  6. Max 2 fixer rounds, then stop and ask a person.
What brokeWhere the fix goes
CP customization (setup script, scripts, tools, docs)Its own PR
Check commands in steps.jsonA person
Main is redA person
Warden itselfCPA tells WA via warden report

Rules: no blind fixes; never loosen a check, add retries or raise timeouts; the fixer can't edit gates; never work around a setup problem in app code.

7. Code review (from the reference app)

  • Engine starts a fresh, read-only reviewer (claude -p) on the diff only, plus the CP's review rules.
  • Must return JSON findings {file, line, severity, summary}. blocking = bug, security, data loss, broken contract · minor = everything else. Findings outside the diff are dropped.
  • Blocking → back to implement → checks + review run again. Max 3 rounds; leftovers go into the PR description.

8. Enforcement — no skipped steps

  • Gates run by the engine, not reported by the CPA.
  • Proof is tied to the commit: any code change after a gate cancels it.
  • Several runs at once: edits are matched by path; Bash by the directory a command works in, then the agent's own link; each subagent has its own session record; the orchestrator is never linked to a ticket; in the ship step, files may be edited while a merge of main is in progress.
  • Hooks:
    • Editing files is blocked in steps that shouldn't change code (e.g. plan).
    • Push / PR / merge blocked unless gates passed for the current commit.
    • Ending a turn is blocked while a run is active and not waiting on a person.
    • The CPA can't write warden's state files directly.

9. State & logs — one home, even with worktrees

Live — not committed

The engine finds the main checkout via git rev-parse --git-common-dir, so every worktree writes to the same place:

<main repo>/.warden/state/<task>/
  run.json       current flow, step, rounds, gate proofs
  events.jsonl   one line per event
  plan.md, triage/, review/

Final — committed

The ship step copies the task's record into the PR:

.warden/history/<task>/

Merged with the code, so the team sees it. Session start reads live state to resume ("WD-0012 stopped at check").

warden site --port <n> — a small local server

  • Run in the CP. Starts a Bun server on the given port (default in warden.json).
  • Reads the JSON in state/ and history/ on each request — nothing is generated or written.
  • One fixed page that fetches the data and refreshes live, so running tasks update on screen.
  • Shows: tasks table → timeline, tokens, findings, verdicts; ticket chart per orchestrated epic; docs rendered as Markdown; code graph when the graph tool built one.
  • Replaces the Next.js docs site and Pipeline Studio. Committed history makes it cover the whole CP team.

12. Reporting, retro & session start — warden stays hidden

  • Reports from any machine that can push to the warden repo reach the WA; without push access they stay on that machine and session start says so once. A report's global key is machine id + R-id.
  • Only WA creates issues. The CPA sees report IDs and plain status only.
  • Session start: runs to resume, layout upgrade needed, newer version available, checks due (offered, never started; auto command checks run in background), orchestration to resume (offered), report status changes, reports stay on this machine (once).
  • Retro: the built-in agent check every 2 days. The CPA offers it, and it runs only on the user's yes.

13. WA as open-source maintainer

  • Triage reads every machine's reports with warden report inbox; the ledger is keyed by machine id / R-id; a fetch that brings new reports rings the doorbell on the WA machine.
  • Triage verdicts, written back with warden report set: real bug snowflake needs info, each with a reason.
  • The report-to-issue map stays in the WA's own ledger. A note never carries a link, issue number or repo name.
  • Small, frequent releases, 0.x until v1. Releases go to stable. CHANGELOG.md + upgrades/vX.Y.Z.md.
  • Before v1: WA triages, decides, releases. From v1: you make the important calls; WA proposes.

14. Project tools

.warden/tools/
  index.ts      export default [ ...tools ]
  tool.ts       contract types + command()
  roles.json    role -> tool name
  <name>.ts     one tool per file (or a folder)
  • The CP writes and owns its tools. Warden ships none and sends no fixes. They are outside .claude/, so edit protection never stalls a step.
  • Commands: warden tools (list), warden tools <name|role> [args], --check (barrel, roles, probes), --init.
  • A tool is an entry in the barrel; tools call each other only through warden tools <other>. In a task worktree, the worktree's tools run.
  • Every engine command has warden's bin first on PATH, so a check can run warden tools e2e run.

Roles warden reads

  • tickets: dag [<epic>], show, set-status; needed for orchestrate and start --ticket.
  • graph: query "<question>", asked before a broad search.
  • pr: its create and merge count as PR and merge commands in the push rules.
  • The site's Graph page reads state/_graph/graphify-out/graph.json (node-link JSON) when it exists; no role needed.

15. Multi-ticket orchestration (ticket DAG)

  • warden orchestrate plan <epic> reads the DAG from the ticket tool and prints waves (checks cycles and unknown blockers).
  • Runs start one at a time, each in its own worktree.
  • One ticket agent per ticket works in parallel; fix steps come back to the orchestrator for the fixer.
  • Ship goes one ticket at a time in wave order, after merging main, so gates run on the merged code; the ticket is marked done.
  • Any blocked, waiting or unmerged ticket stops it, and running it again goes on.
